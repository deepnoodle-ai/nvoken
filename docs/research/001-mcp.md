# MCP, the Model Context Protocol

**Owner:** Anthropic, now governed by the Agentic AI Foundation
**Standardizes:** Agent to tools and data
**Current revision:** `2026-07-28`
**Status here:** Research. nvoken is already an MCP client, so this is a
compatibility assessment rather than an adoption question.
**Date:** 2026-08-13

## Where nvoken already stands

nvoken consumes MCP today. `CreateInvocationRequest.mcp_servers` accepts public
HTTPS streamable-HTTP endpoints, each with a `name` up to 24 characters that
prefixes its tools as `<name>__<tool>` in the model's view. `mcp_server_headers`
carries per-server credentials, and `MCPToolExclusion` reports tools nvoken
refused to expose with a `reason` of `not_allowlisted`, `invalid_name`,
`name_collision`, `invalid_schema`, `schema_too_large`, or `schema_too_deep`.

So nvoken is an MCP host embedded in a durable runtime. Everything below is
about keeping that client current, plus one strategic question at the end.

## What changed in 2026-07-28, and what it costs us

This revision is the largest break in MCP's history. The core went stateless.

**The handshake is gone.** `initialize` and `notifications/initialized` are
removed, along with the `Mcp-Session-Id` header. Every request now carries what
the handshake used to establish, in `_meta`:
`io.modelcontextprotocol/protocolVersion`,
`io.modelcontextprotocol/clientCapabilities`, and
`io.modelcontextprotocol/clientInfo`. Servers identify themselves per result via
`io.modelcontextprotocol/serverInfo`. A mismatch returns
`UnsupportedProtocolVersionError`.

**`server/discover` is mandatory on servers.** It advertises supported protocol
versions, capabilities, and identity. Clients may call it before anything else
to pick a version up front.

**Server-initiated requests are gone, replaced by MRTR.** Multi Round-Trip
Requests replace `roots/list`, `sampling/createMessage`, and
`elicitation/create`. A server that needs more information returns an
`InputRequiredResult` with `resultType: "input_required"` and an `inputRequests`
field. The client retries the original request carrying `inputResponses`. Every
result now has a required `resultType`, either `"complete"` or
`"input_required"`.

**Notifications moved.** The HTTP GET endpoint and
`resources/subscribe`/`unsubscribe` are replaced by `subscriptions/listen`, a
single long-lived POST-response stream you opt into by notification type.
Request-scoped notifications such as `notifications/progress` still flow on the
response stream of their own request.

**List results are cacheable.** `tools/list`, `prompts/list`, `resources/list`,
`resources/read`, and `resources/templates/list` now require `ttlMs` and
`cacheScope` (`"public"` or `"private"`) via a `CacheableResult` interface.
Servers should return tools in a deterministic order so clients can cache and
so prompt caches hit.

**New required headers.** Streamable HTTP POSTs must carry `Mcp-Method` and
`Mcp-Name`. Custom headers can be sourced from tool parameters via
`x-mcp-header`.

**Roots, Sampling, and Logging are deprecated**, with a minimum twelve-month
window under the new feature lifecycle policy. The suggested migration away
from Sampling is to "integrate directly with LLM provider APIs instead", which
is a fair description of what nvoken is.

**Tasks moved to an official extension** (`io.modelcontextprotocol/tasks`),
replacing the blocking `tasks/result` with `tasks/get` polling and adding
`tasks/update` for client-to-server input.

### The change that matters most to us

> Remove SSE stream resumability and message redelivery (the `Last-Event-ID`
> header and SSE event IDs) from the Streamable HTTP transport. A broken
> response stream loses the in-flight request; clients MUST re-issue it as a new
> request with a new request ID.

MCP deleted the exact mechanism nvoken's own streaming protocol is built on. Our
[streaming protocol](../reference/streaming-protocol.md) is durable cursors and
`Last-Event-ID` resumption from end to end. MCP has concluded that a tool
protocol should not carry that weight and has pushed durability up to the
application.

That is good news for nvoken's positioning and bad news for one implementation
detail. A tool call that drops mid-flight is now unambiguously nvoken's problem
to retry, and MCP will not help us tell a lost response from a slow one. Our
retry has to be safe without protocol support, which means idempotency at the
tool boundary is now our concern rather than a shared one.

## Compatibility work this implies

Ordered roughly by how soon it bites. All of it lands in `nvoken-cloud`'s MCP
client, not in this repository.

1. **Send `_meta` on every request** and stop relying on any handshake state.
2. **Stop sending `Mcp-Session-Id`.** Servers on the new revision ignore it;
   some will reject unknown headers.
3. **Handle `resultType`.** Treat a missing value as `"complete"` for older
   servers, as the spec requires.
4. **Implement MRTR.** A tool call can now come back asking for more input
   rather than returning a result. nvoken has to decide whether an
   `input_required` result parks the Invocation the way a host tool does, or is
   resolved internally. See the mapping below, because this is a genuine design
   choice rather than a mechanical port.
5. **Add `Mcp-Method` and `Mcp-Name` headers.**
6. **Honor `ttlMs` and `cacheScope`** on list results. nvoken re-lists tools per
   turn today; caching them is a direct latency and cost win.
7. **Call `server/discover`** for version selection instead of assuming.
8. **Plan for the deprecations.** We do not use Sampling or Roots, so the
   twelve-month window is not urgent, but anything that depends on Logging needs
   a path to OpenTelemetry.

## MRTR is nvoken's waiting state, in a different vocabulary

The isomorphism is close enough to be worth naming:

| MCP 2026-07-28 | nvoken |
| --- | --- |
| `InputRequiredResult` | Invocation status `waiting` |
| `inputRequests` | `pending_tool_calls` |
| `inputResponses` on retry | `POST /v1/invocations/{id}/tool-results` |
| `requestState` for correlation across retries | `tool_call_id` |
| `resultType: "complete"` | terminal Invocation status |

Both designs concluded that a long-running call should return control rather
than block, and that the caller resumes by re-presenting the original request
with the missing input attached. MCP arrived there by deleting server-initiated
requests; nvoken arrived there because a turn has to survive a process restart.

The open question this creates: when an MCP tool returns `input_required`,
whose input is it asking for? If it needs the end user, that is nvoken's
ask-user path and the Invocation should park. If it needs something nvoken can
supply itself, parking a turn on it would be a regression. The spec does not
make that distinction for us.

## The tasks extension is a smaller nvoken

`io.modelcontextprotocol/tasks` gives servers a handle for long-running work,
polled with `tasks/get` and updated with `tasks/update`. That is nvoken's
Invocation with a narrower scope: no durable transcript, no session, no
provider abstraction, and explicitly no resumable stream.

Two readings, both worth holding:

- **Defensive.** The gap nvoken fills is being partially specified inside MCP.
  If a tool server can hand back a durable task handle, some of the reasons to
  reach for a runtime weaken.
- **Opportunistic.** An nvoken MCP server whose tools return task handles is a
  natural product shape. Someone's agent calls `run_agent`, gets a handle, and
  polls it. The durability, transcript, and recovery are ours; the calling
  convention is theirs. This is a smaller and more likely first step than A2A.

## Recommendation

**Adopt as a client, on a schedule.** The compatibility list above is real work
and none of it is optional if we want to keep talking to current servers. Item 4
needs a design decision before it can be implemented.

**Do not adopt as our own wire format.** MCP just removed the property nvoken
exists to provide. Speaking MCP inward, at the tool boundary, is right. Speaking
it outward, as how a host follows a turn, would mean giving up resumption.

**Consider an nvoken MCP server as a product surface**, using the tasks
extension. Cheaper than A2A, and it puts nvoken inside Claude and every other
MCP host.
