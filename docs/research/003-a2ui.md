# A2UI, the Agent to UI Protocol

**Owner:** Google, with CopilotKit as a design partner
**Standardizes:** The UI payload an agent emits, not the connection carrying it
**Current version:** v0.9.1, in the stable v0.9 family. v0.9 landed April 2026.
**Status here:** Research. Least directly relevant of the five, with one narrow
question we should answer deliberately rather than by accident.
**Date:** 2026-08-13

## What it is

A declarative JSON format for describing user interface intent. The agent does
not send code or markup. It sends a description of components to draw, chosen
from a catalog the client controls, and the client renders them with its own
native widgets. Renderers exist for web, Flutter, Angular, and Lit.

The security property follows from the catalog. An agent can only ask for
components the client has pre-approved, so a compromised or manipulated model
cannot inject arbitrary markup or script. It can only request a Card that the
client already knows how to draw. That removes a class of injection risk rather
than filtering for it.

## The message model

Four server-to-client message types, streamed as JSON objects:

- **`createSurface`** opens a surface with a `surfaceId` and a `catalogId`.
- **`updateComponents`** adds or modifies component definitions in a surface.
- **`updateDataModel`** populates or changes the data components display.
- **`deleteSurface`** removes a surface.

Components live in a flat map keyed by id, with tree structure expressed as id
references in an adjacency list. Rendering can begin as soon as the `root`
component is defined and fills in progressively as more messages arrive.

Structure and data are strictly separated. Components carry structural and
visual properties. The data model carries only values, addressed by JSON Pointer
paths, and components bind to it with `path` references like `"/user/name"`.

### Update semantics are replacement, not patching

Worth stating precisely, because it is the opposite of AG-UI's approach and it
is the exact question we spent a whole pass on for our own transcript model:

- `updateDataModel` with a `path` replaces the value at that path.
- `updateDataModel` without a `path` replaces the entire data model.
- An omitted `value` removes the key.

No JSON Patch, no merge. A2UI chose "always replace, at an addressable path"
where AG-UI chose "snapshot plus RFC 6902 deltas". A2UI's rule is simpler to
implement correctly and sends more bytes. Given how much ambiguity our own
replace-versus-merge boundaries produced, the simplicity is worth respecting.

## Relevance to nvoken

Lower than the others, and it is worth being clear about why rather than
hand-waving.

nvoken is a runtime. It admits a turn, runs a model, survives a restart, and
hands back a transcript. It has no view layer and should not grow one. A2UI
describes what a view should draw. Those are different jobs at different layers,
and there is no version of "nvoken adopts A2UI" that makes sense as stated.

**But there is a pass-through question, and it is real.**

If a customer's agent produces generative UI, that payload has to travel from
the model, through nvoken's transcript, to their frontend. Today it would travel
as either structured output or an ordinary text block containing JSON. Both work.
Neither is labeled, so nothing downstream can tell a UI payload from prose
without knowing in advance.

That question is live for us for an unrelated reason. Our content block union is
already incomplete: `SessionContentBlock` declares a closed discriminator that
omits `thinking` and `redacted_thinking`, both of which the runtime emits and the
console renders. Recorded as N5 and I11 in the
[streaming protocol reference](../reference/streaming-protocol.md). We are going
to have to decide how that union grows. Whether a UI payload block is one of the
members it grows by is a decision to make on purpose.

Three options, in order of increasing commitment:

1. **Do nothing.** Hosts put A2UI messages in structured output and label them
   themselves. Costs us nothing and works today.
2. **Let the union carry an opaque typed block.** A generic block type meaning
   "structured payload with a declared media type", which a host can use for
   A2UI or anything else. No A2UI knowledge in nvoken.
3. **Model A2UI specifically.** Validate the payload, version it, expose it as a
   first-class block type.

Option 3 is wrong for now. A2UI is at v0.9 and nvoken would be taking on a
schema it does not control, in service of a use case no customer has asked us
for. Option 2 is defensible on its own merits regardless of A2UI, because
"typed opaque payload" is a gap in the content model independent of generative
UI.

## How it sits next to the others

The three UI-adjacent protocols are not competing, and it helps to hold the
distinction:

- **AG-UI** is the connection. Streaming, state sync, lifecycle, approvals.
- **A2UI** is the payload. What to draw, once you have a connection.
- **MCP Apps** is the inverse direction. Your product rendered as a surface
  inside someone else's agent host.

An agent can emit A2UI messages over an AG-UI connection, and CopilotKit has
already wired exactly that. So if we ever do carry UI payloads, the pairing is
AG-UI plus A2UI, and our AG-UI adapter is the natural place for it to ride.

## Recommendation

**Not relevant to adopt.** No compatibility work, no tracking obligation.

**Answer the pass-through question when we next touch the content block union**,
which N5 says we must do anyway. Prefer option 2, a generic typed payload block,
over anything A2UI-specific. That serves generative UI without binding nvoken to
a v0.9 schema owned by someone else.

Revisit if a customer ships generative UI on nvoken and tells us the untyped
path hurt.
