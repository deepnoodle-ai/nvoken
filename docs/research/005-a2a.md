# A2A, the Agent2Agent Protocol

**Owner:** Started at Google, governed by the Linux Foundation since June 2025.
ACP merged into it.
**Standardizes:** Agent to agent
**Current version:** v1.0, 2026. 150+ supporting organizations, integrated
across Google, Microsoft, and AWS platforms.
**Status here:** Research. The closest structural match to nvoken's own model,
and the largest piece of work if we pursue it.
**Date:** 2026-08-13

## What it is

A specification for how independent agents discover each other, delegate work,
and exchange results across organizational boundaries. JSON-RPC 2.0 over HTTP,
with gRPC and HTTP+JSON bindings also defined.

**Discovery** is the Agent Card, a JSON metadata document an A2A server
publishes describing `id`, `displayName`, `description`, `capabilities`,
`skills`, `agentInterfaces`, `securitySchemes`, and `extensions`. A server whose
`capabilities.extendedAgentCard` is true also serves a richer authenticated
version through `GetExtendedAgentCard`.

**Work** is the Task: `id`, `contextId`, `status`, `artifacts`, and `history`.
Tasks are stateful and move through a defined lifecycle.

**Operations** are `SendMessage`, which returns immediately with either a Task or
a direct Message; `SendStreamingMessage` for live updates;
`GetTask`, which takes an optional `historyLength`; `CancelTask`, which requests
cancellation without guaranteeing it; and `SubscribeToTask` for reattaching a
stream.

**Results** distinguish two things nvoken does not. Messages are communication
between client and agent, carrying `messageId`, `role` (`ROLE_USER` or
`ROLE_AGENT`), and `parts`. Artifacts are outputs, carrying `parts` plus
metadata like `mediaType` and `url`. The spec is explicit that results should be
returned as Artifacts so that communication and output stay separable.

## The lifecycle maps onto ours almost exactly

Eight states against our eight:

| A2A `TaskState` | nvoken `InvocationStatus` | Notes |
| --- | --- | --- |
| `SUBMITTED` | `queued` | Same meaning |
| `WORKING` | `running` | Same meaning |
| `INPUT_REQUIRED` | `waiting` | Both mean parked pending caller input |
| `AUTH_REQUIRED` | none | We refuse at admission instead of parking |
| `COMPLETED` | `completed` | Same meaning |
| `FAILED` | `failed` | Same meaning |
| `CANCELED` | `cancelled` | Same meaning, one L against two |
| `REJECTED` | none | We refuse at admission, so it is never a status |
| none | `incomplete` | A limit stopped a turn cleanly. A2A has no equivalent |
| none | `budget_hold` | Budget stop, resumable. A2A has no equivalent |

Two agreements and two disagreements, and both disagreements are informative.

A2A models refusal as a task state; we model it as an admission failure that
never creates an Invocation. Ours is the stronger position for auditing, since a
refused nvoken admission still leaves an `AdmissionAttempt` record, and it is the
weaker one for A2A compatibility, since a client expecting to poll a rejected
task would find nothing to poll.

Our `incomplete` and `budget_hold` have nowhere to go. Both would have to collapse
into `FAILED` or `COMPLETED` at the boundary, and both distinctions exist because
they were worth making. `incomplete` in particular carries "the answer so far is
valid and carries forward", which flattening destroys.

The structural mapping is just as close:

| A2A | nvoken |
| --- | --- |
| Task | Invocation |
| `contextId` | Session |
| `SendMessage` | `POST /v1/invocations` |
| `GetTask` with `historyLength` | `GET /v1/invocations/{id}` plus transcript |
| `CancelTask` | `POST /v1/invocations/{id}/cancel` |
| `SubscribeToTask` | `GET /v1/invocations/{id}/stream` |
| Push notifications | Webhooks (`invocation.waiting`, `invocation.settled`) |
| Agent Card | Agent Definition, roughly |

## Where we are stronger, and it is the same place as always

On resumption, A2A says this plainly:

> Clients using streaming to retrieve task updates MAY not receive all status
> update messages if the client is disconnected and then reconnects. Messages
> MUST NOT be considered a reliable delivery mechanism for critical information.

The recommended path for reliability is push notifications, not streaming.

That is the third time in this document set. MCP deleted SSE resumability. AG-UI
never had a cursor. A2A tells you outright not to trust the stream. Every one of
these protocols concluded that durable delivery belongs above them.

nvoken's stream is resumable by cursor and replays saved state from any
position. So satisfying A2A's streaming contract is not work, it is a
restriction: we would be permitted to lose messages and would simply not. An
nvoken-backed A2A server would be more reliable than the specification requires,
which is a fine place to be.

## What compatibility would look like

An A2A server facade in front of nvoken. Nothing about our core changes; A2A
becomes another way in.

- **Agent Card** generated from an Agent Definition, with `skills` derived from
  the tool set and `capabilities.streaming` true.
- **`SendMessage`** onto `createInvocation`, returning a Task view of the
  Invocation. Our `idempotency_key` has no A2A counterpart, so the facade owns
  generating one.
- **`GetTask`** onto the Invocation read plus the transcript, projecting
  messages into A2A Messages and structured output into Artifacts.
- **`SubscribeToTask`** onto the Invocation stream, translating frames into A2A
  status and artifact events.
- **`CancelTask`** onto cancel, which already returns the turn unchanged when it
  has finished, matching A2A's "not guaranteed" language.

Two things need decisions rather than translation. The `incomplete` and `budget_hold`
states have no target, and the Message-versus-Artifact split does not exist in
our transcript. We have messages with content blocks and a separate
`structured_output`, which is close to the split but not aligned with it: a
tool-only turn produces Artifacts in A2A's sense and nothing we would call
structured output.

## Recommendation

**Not now, and not because it is uninteresting.**

A2A is the most strategically significant of the five. It is where cross-vendor
agent delegation is settling, the governance is neutral, and the adoption is
broad enough that being absent from it eventually costs something. The mapping
onto our model is unusually clean, which suggests both designs found the same
shape because it is the right one.

But it is also the largest build, it is a new public surface with its own
compatibility burden, and the demand signal should come first. Nobody has asked
us for it. AG-UI, by contrast, has a much smaller first step and sharpens our
own protocol as a side effect.

The right sequence is AG-UI, then reassess. If A2A traffic starts arriving at
customers who host on nvoken, that is the signal, and the facade above is the
plan.

**Track two things in the meantime.** Whether `incomplete` and `budget_hold` acquire
A2A equivalents, since a spec that grows toward our states makes the facade
cheaper. And whether A2A's push-notification path becomes the dominant one in
practice, because if it does, our webhooks are already most of an A2A
integration.
